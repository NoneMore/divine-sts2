# 01: Enumerate single-prompt Ancient rewards

**What to build:** For one character, Ascension and run seed, every legal non-skip option that an offered Ancient choice opens at a single reward-set, bundle or relic option prompt becomes its own replayable first-combat scenario. Today a scenario generation element resolves each nested prompt by taking the first legal action, so one element yields one row per offered Ancient choice and nothing more; after this ticket an element yields one row per legal non-skip option at that prompt, each with its own ordered recipe, at a per-branch cost that keeps deeper recursion affordable.

This ticket carries the branch mechanism itself, so it also settles and states what a sibling branch's state is obtained from. The branched-from prompt's own state handle is what the worker is asked for, and it serves one as a run reconstruction plus a replay of the actions that reached the prompt: a nested prompt state carries a pending choice or an open reward set, which the shipped save schema does not represent, so no nested state can be snapshotted and no cheaper checkpoint exists without native work. The alternative — restoring the Ancient offer's checkpoint, the one state this build does snapshot, and letting the driver replay the prefix — is measured beside it.

One prompt-kind vocabulary (which action kind means card-select prompt, option pick, reward set and skip) serves the generator, the materializer and acceptance, so prompt-kind knowledge stops being repeated per call site and the kinds that follow in later tickets plug into one place. It extends the module that already reconciles the two encoders' decision words rather than becoming a second table. Skip eligibility is decided there in both of the forms this build has: an action kind that is a skip of its own, and an ordinary kind whose selection says skip. A prompt kind the vocabulary does not know is that branch's failure row, naming the kind it did not know.

Blocked by: None (can start immediately).

Status: ready-for-agent

- [ ] A reward-set, bundle or relic option prompt opened by an offered Ancient choice produces one recorded branch per legal non-skip option, in the order the run offered them. Both forms of skip produce no branch: a kind that is a skip of its own, and an ordinary kind whose selection says skip.
- [ ] Each success row records the offered Ancient choice, the prompt kind, the selected option's index and the identity the shared vocabulary declares for that kind, plus the complete pre-action combat initial state; its recipe materializes the same state. What a reward-set step is selected by today is recorded here; recording the selected reward's own identity stays with ticket 03.
- [ ] A failed option produces its own failure row with the recipe resolved so far and does not suppress its siblings.
- [ ] One prompt-kind vocabulary decides prompt kind, skip eligibility and option identity for generation, materialization and acceptance, and a prompt kind it does not know is that branch's failure row with that kind named, never a default and never a batch-ending error.
- [ ] The mechanism that yields a sibling branch's state is stated for callers with its measured per-branch cost, beside the cost of restoring the Ancient offer's checkpoint and replaying the prefix from the driver, and beside the cost of a whole run drive, on a named fixed request. A branch state the worker can no longer restore is an explicit failure rather than a wrong row.
- [ ] Branch, row and shard order are deterministic; a fixed request, build and worker count gives byte-identical artifacts, and a different worker count leaves the row set identical.
- [ ] The shipped-game record acceptance and parity sample that pin one row per offered Ancient choice now pin one row per retained branch, so what they check is the enumeration the generator performs.
- [ ] Existing first-combat scenarios that need no nested option stay reachable, reproducible and unchanged.

## Comments

- **Refinement round, 2026-09-26.** Kept as one ticket rather than split into vocabulary, branch and measurement slices; the acceptance criteria above were rewritten so each is decidable against the present code. Decisions recorded in this round: the prompt-kind vocabulary extends the module that already reconciles the two encoders' decision words; a prompt kind the vocabulary does not know is that branch's failure row; skip has two forms here (`skip_custom_rewards` and `skip_treasure` as kinds of their own, and `choose_reward` with `skip: true` / `option_index: -1` and `choose_room_reward` with `option_index: -1` as skip selections on an ordinary kind); a nested prompt state carries a pending choice or an open reward set, so the run-snapshot path refuses it and a nested sibling restore is a reconstruction plus a history replay, with a cheap nested checkpoint left as native work outside this ticket; and option identity is per prompt kind (a bundle's option ids, a relic option's index and model id), while a reward set's own identity does not fit the present nested-choice record shape and therefore stays with ticket 03.
