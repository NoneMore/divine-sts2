# Act 1 combat 1 scenarios

Status: draft — awaiting review. Becomes `ready-for-agent` once the owner signs off, then splits into tickets under `issues/`.

## Problem Statement

Someone training or evaluating act-1 combat policies needs many starting points that begin at the fight which actually opens a run. Today the simulator can be reset straight into any combat a caller invents, but it cannot be asked for the combat the shipped game would present for a given character, Ascension and run seed. So the training distribution has no relationship to real runs, and nothing generated can be checked against the shipped game — the Ancient room that a real run always passes through is never entered, and two consequences of skipping it (below) silently change the first fight.

## Solution

A batch generator that, for a Cartesian product of characters × Ascensions × run seeds, drives the simulator through the act-1 Ancient room the way the shipped game does, resolves one Ancient choice per record, and captures the combat initial state of the first node — which is always a normal monster node. Every record carries enough run-start facts to be reproduced by hand in the shipped game: paste the run seed into the custom run screen, pick the recorded Ancient choice, and the same fight is there. Parity is a property of what the game *offers*; which Ancient choice a record takes is ours to make, as long as it is legal and recorded (ADR-0003).

Scope of the first cut: a few thousand records, generated by the simulator, with the shipped game used as an acceptance oracle rather than as the generator.

## User Stories

1. As an RL practitioner, I want to ask for the first combat of a run identified by character, Ascension and run seed, so that my training distribution is made of situations real runs actually produce.
2. As an RL practitioner, I want a batch request expressed as a Cartesian product of dimension sets, so that I can enumerate characters × Ascensions × seeds in one command instead of scripting the loop myself.
3. As an RL practitioner, I want each record to contain the full combat initial state — enemies with their generated HP, the ordered draw pile, the hand, relics, potions, HP, gold and the RNG counters — so that I can start an episode from it without replaying the run.
4. As an RL practitioner, I want the Ancient options that the run seed offers recorded on the record, so that my policy can condition on the run's opening situation.
5. As an RL practitioner, I want the Ancient choice that the record took to be part of the record's identity, so that two records for the same seed and different choices are not confused with each other.
6. As an RL practitioner, I want the act-1 Act variant, the chosen node's coordinate and type, the encounter id, and the floor counters on the record, so that I can group, filter and audit records without re-deriving anything.
7. As an RL practitioner, I want records that are reproducible in the shipped game, so that a surprising sample can always be checked by hand.
8. As an RL practitioner, I want the record to be a portable recipe rather than a state snapshot, so that a corpus generated against one game build stays readable and re-runnable after the game updates.
9. As an RL practitioner, I want a run seed to be recorded in the canonical form the shipped game derives, so that pasting it into the custom run screen reproduces the record.
10. As an RL practitioner, I want the raw seed string kept as a diagnostic field when the caller passes a non-canonical one, so that I can tell canonicalisation happened.
11. As an RL practitioner, I want every Ancient choice the run seed actually offers to be enumerated, so that coverage over openings is complete rather than sampled.
12. As an RL practitioner, I want a deterministic rule to resolve the nested choice that some Ancient choices open, so that a record is reproducible without me answering prompts.
13. As an RL practitioner, I want the nested choice that was made recorded, so that I can audit it and later replace the rule.
14. As an RL practitioner, I want records sharded across workers with a summary file, so that a large batch is resumable and a single failed seed does not destroy the run.
15. As an RL practitioner, I want failures written to the output with a reason instead of being dropped, so that the corpus cannot develop a silent bias.
16. As an RL practitioner, I want the same inputs to produce byte-identical records on a re-run, so that a corpus can be regenerated and diffed.
17. As a maintainer, I want the batch logic to live inside the Python package with only a thin command-line wrapper, so that it is importable and testable instead of being the eighty-first sibling script.
18. As a maintainer, I want the simulator to enter the Ancient room through the shipped game's own code path, so that the floor bookkeeping and every relic effect come from the game rather than from a reimplementation.
19. As a maintainer, I want the combat observation to name its encounter, so that a parity check has something to compare and an audit can identify a fight.
20. As a maintainer, I want the observation to expose the floor counter that the Ancient room advances, so that the parity gap that motivated this feature is observable instead of inferred.
21. As a maintainer, I want the published observation schema to match what the environment actually emits for run-mode captures, so that the schema stops being documentation that contradicts the code.
22. As a maintainer, I want the acceptance oracle to drive the shipped game through the full-app bridge, so that parity is demonstrated against the real thing rather than asserted.
23. As a maintainer, I want the oracle runnable on a machine whose game install and local app-data live on different drives, so that acceptance is not silently machine-specific.
24. As a maintainer, I want the offline parts of acceptance to run under CI, with the parts that need the shipped game kept separate, so that regressions are caught without a game install.

## Implementation Decisions

**Enumeration and identity**

- The request is a Cartesian product over dimension sets: characters (the five the shipped game exposes), Ascensions (0–10), and run seeds supplied as strings. Target scale 10³–10⁴ records; the design must survive 10⁵.
- A record's identity is `(character, ascension, canonical run seed, Ancient choice index, nested choices)`. Ancient choice identity is recorded twice — index (for exact replay) and relic model id (for human reading and robustness against option reordering).
- Only Ancient choices the run seed actually offers are enumerated, so a `(character, ascension, seed)` triple yields as many records as the run offers choices (normally three). Forcing a choice the run does not offer is not supported.
- Nested choices (card select, reward set, bundle pick) are resolved by a fixed deterministic rule — smallest legal index — and the resolved choice is recorded. The Cartesian product does not expand over nested choices.
- The act-1 Act variant is an explicit parameter of the request, defaulting to the variant the shipped game's `act_selection` roll produces from the run seed. Changing the default — to treat every variant as discovered — is deferred; see Further Notes.

**Run construction**

- Runs use the shipped game's starting loadout for the requested character and Ascension. Caller-supplied decks, relics or potions are not supported: swapping them would produce a situation the shipped game cannot reach.
- Run seeds are canonicalised generator-side exactly as the shipped game does when a run begins, and the canonical form is what the request carries and the record stores. The raw string is kept only as a diagnostic.
- The simulator enters the act-1 Ancient room at run start by travelling to the Ancient node the way the shipped game does, rather than by entering the event directly. That single decision repairs the floor bookkeeping and provides the Ancient choice dimension.
- The Ancient choice is applied through the game's own option-completion path, so that relic effects and any RNG they consume come from the game.
- The first fight is reached by travelling to a row-1 node, which is always a normal monster node and always a weak encounter.

**Observation contract**

- The combat observation gains the encounter id, and the run block gains the floor counter the Ancient room advances plus act index and act floor, so that a combat observation is self-describing and the parity gap is directly observable.
- The published canonical-state schema is brought in line with what run-mode captures actually emit, instead of describing only the combat-mode shape.
- Both the observation schema version and the hash schema version are bumped. Every existing golden hash and determinism assertion is regenerated; this is cheapest now, while no generated corpus exists.
- The new fields are inside the state hash. Excluding them would stop the hash covering the state and weaken restore's divergence detection.

**Batch generator**

- The generator drives the simulator, not the shipped game. The shipped game is used only as the acceptance oracle.
- Enumeration, retry, sharding and output live in the Python package; a thin command-line wrapper exposes them. The wrapper follows the repository's existing command-line shape (worker count, character list, Ascension, output directory, compression) rather than inventing a new one.
- Output is shards of compressed JSONL under an artifact root, one shard per worker, plus a summary file — the convention the repository already uses for corpora. Every row carries a schema tag.
- A failed element is written with its reason. Nothing is dropped silently.
- Records carry the recipe and the combat initial state. No portable snapshot is stored; a session-scoped fast-start handle may be added later as an optimisation, explicitly not a record field.

**Oracle prerequisites**

- The Python path-discovery module gains a configurable sandbox root, defaulting to the game's own volume, so that the bridge's hard links work instead of falling back to a full copy of the install. Nothing else in discovery is changed here.

## Testing Decisions

- **What makes a good test here:** assert on the record and on the observation contract, not on how the generator loops. The two things worth protecting are determinism (same inputs, byte-identical output) and parity (the record equals what the shipped game produces).
- **Offline, CI-visible (pytest under `tests/`):** canonicalisation of run seeds; expansion of a request into the expected record set, including that only offered Ancient choices appear; schema validation of emitted records against the published canonical-state schema, which is what stops the schema drifting again; a round trip that takes a record's recipe and reaches the same combat initial state through the simulator.
- **Needs the shipped game (`*_acceptance.py` convention):** the full-app bridge parity run. For a fixed sample of roughly a dozen scenarios spanning characters and Ascensions, drive the shipped game with the same run seed, Ascension, Act variant and Ancient choice, and compare the first combat's monster ids and HPs, the ordered draw pile, and the HP/gold/relic/potion state field by field.
- **Gate for this feature:** the fixed sample passes, and determinism holds. A coverage-driven campaign — every character × every Ascension × every reachable Ancient choice — is deliberately not the gate, but is the first thing to run once the feature lands, because the nested-choice paths are where divergence is most likely.
- **Prior art:** the repository already has map determinism and room-entry acceptance scripts, and a differential harness that compares simulator traces against shipped-game traces; the parity run should reuse that comparison style rather than invent one.

## Out of Scope

- Caller-supplied starting loadouts. Generating "this fight with a different deck" is a different feature, and mixing it into a parity corpus would corrupt the corpus's meaning.
- Enumerating nested choices as extra dimensions of the product.
- Persisted state snapshots. The simulator's state handle is a branch identifier tied to a worker's local history, not a portable artifact.
- Acts beyond act 1, and the Ancient rooms of later acts.
- Non-parity and debug paths for forcing an Ancient choice the run does not offer.
- Repairing Steam-root discovery. It is a real defect, but it belongs to the existing single-discovery-policy work, and a configured game root is an adequate workaround for this feature.
- Scale beyond 10⁵ records.

## Further Notes

- **Two parity gaps motivate the scope, and only one of them is repaired by entering the Ancient room.** Skipping the Ancient room leaves the floor counter one entry behind the shipped game, which seeds the per-encounter generator and therefore changes randomised monster composition even when the encounter id matches — entering the room repairs that. The second gap is independent: act 1 has two Act variants, the shipped game rolls one from the run seed, and the simulator currently hard-codes the default one, so for seeds whose act 1 is the other variant every act-1 room is the wrong one. Map topology is unaffected; the pools are not. See `.scratch/act1-combat1-scenarios/parity-findings.md` for the evidence.
- **A chosen Ancient choice may legitimately change the first fight.** Some choices consume RNG that the first combat then uses for enemy HP. That is not a defect: parity is defined against a shipped-game run that made the same choice, which is why the choice is part of the record's identity rather than optional metadata.
- **Skipping the Ancient room does not shift any RNG stream.** The Ancient event draws from its own generator, so the older worry that entering it would change map, encounter or shuffle parity for a seed is settled as unfounded.
- **A pending ADR question.** The follow-up default of treating every Act variant as discovered touches `SaveManager.Progress.DiscoveredActs`, which is a discovery field, and ADR-0001 states that a fully unlocked run does not imply discovered content. When that default is implemented, ADR-0001 needs an explicit clarifying sentence or a new ADR; it should not be adopted silently.
- **Environment findings from de-risking the oracle.** The shipped game is installed in a secondary Steam library while local app-data lives on another drive, so the bridge's hard links fail and its copy fallback exhausts the local drive. The bridge itself works — real game workers start headlessly and answer — but the sandbox root must sit on the game's volume. Both this and the Steam-root discovery defect are recorded here rather than fixed broadly.
