# Act 1 combat 1 scenarios

Status: draft — awaiting review. Becomes `ready-for-agent` on owner sign-off, then splits into tracer-bullet tickets under `issues/`.

## Problem Statement

Someone training or evaluating act-1 combat policies needs many starting points that begin at the fight which actually opens a run. Today the simulator can be reset straight into any combat a caller invents, but it cannot be asked for the combat the shipped game would present for a given character, Ascension and run seed. So the training distribution has no relationship to real runs, and nothing generated can be checked against the shipped game — the Ancient room that a real run always passes through is never entered, and two consequences of skipping it (Further Notes) silently change the first fight.

## Solution

A batch generator that, for a Cartesian product of characters × Ascensions × run seeds, drives the simulator through the act-1 Ancient room the way the shipped game does, resolves one Ancient choice per record, and captures the combat initial state of the first node — which is always a normal monster node. Every record carries enough run-start facts to be reproduced by hand in the shipped game: paste the run seed into the custom run screen, pick the recorded Ancient choice, and the same fight is there. Parity is a property of what the game *offers*; which Ancient choice a record takes is ours to make, as long as it is legal and recorded (ADR-0003).

Scope of the first cut: a few thousand records, generated by the simulator, with the shipped game used as an acceptance oracle rather than as the generator.

## User Stories

1. As an RL practitioner, I want to ask for the first combat of a run identified by character, Ascension and run seed, so that my training distribution is made of situations real runs actually produce.
2. As an RL practitioner, I want a batch request expressed as a Cartesian product of dimension sets, so that I can enumerate characters × Ascensions × seeds in one command instead of scripting the loop myself.
3. As an RL practitioner, I want each record to contain the full combat initial state — enemies with their generated HP, the ordered draw pile, the hand, relics, potions, HP, gold and the RNG counters — so that I can start an episode from it without replaying the run.
4. As an RL practitioner, I want the Ancient options that the run seed offers recorded on the record, so that my policy can condition on the run's opening situation.
5. As an RL practitioner, I want the Ancient choice that the record took to be part of the record's identity, so that two records for the same seed and different choices are not confused with each other.
6. As an RL practitioner, I want the act-1 Act variant, the chosen node's coordinate and type, and the encounter id on the record, so that I can group, filter and audit records without re-deriving anything.
7. As an RL practitioner, I want the row-1 node picked for me by a fixed, documented rule rather than left to my choice, so that two runs of the same request cannot disagree about which fight they mean.
8. As an RL practitioner, I want to be told the exact set of fields that is guaranteed to match the shipped game, so that "reproducible" is a checkable claim rather than a mood.
9. As an RL practitioner, I want the record to be a portable recipe rather than a state snapshot, so that a corpus generated against one game build stays readable and re-runnable after the game updates.
10. As an RL practitioner, I want a run seed to be recorded in the canonical form the shipped game derives, so that pasting it into the custom run screen reproduces the record.
11. As an RL practitioner, I want the raw seed string kept as a diagnostic field when the caller passes a non-canonical one, so that I can tell canonicalisation happened.
12. As an RL practitioner, I want a request whose seeds collide after canonicalisation to be rejected instead of silently deduplicated, so that I never train on a corpus whose size I misunderstand.
13. As an RL practitioner, I want every Ancient choice the run seed actually offers to be enumerated, so that coverage over openings is complete rather than sampled.
14. As an RL practitioner, I want a deterministic rule to resolve the nested choice that some Ancient choices open, so that a record is reproducible without me answering prompts.
15. As an RL practitioner, I want the nested choice that was made recorded, so that I can audit it and later replace the rule.
16. As an RL practitioner, I want records sharded across workers with a summary file, so that a large batch is resumable and a single failed seed does not destroy the run.
17. As an RL practitioner, I want a failure recorded as its own row with a reason and the recipe resolved so far, so that the corpus cannot develop a silent bias and I can count what failed.
18. As an RL practitioner, I want the same request with the same worker count to produce byte-identical output, so that a corpus can be regenerated and diffed, and so that a mismatch means a real change.
19. As an RL practitioner, I want record order and shard assignment fixed by the request rather than by completion timing, so that a slow worker cannot reorder my corpus.
20. As a maintainer, I want to know precisely which fields the shipped-game comparison must cover, so that acceptance is a checklist rather than sample-and-hope.
21. As a maintainer, I want the full-app bridge's existing state observation extended to carry every contract field, so that the oracle can actually compare them instead of comparing a subset.
22. As a maintainer, I want a parity mismatch to name the field path that differed, so that a failure localises itself.
23. As a maintainer, I want the batch logic to live inside the Python package with only a thin command-line wrapper hanging off the existing console entry point, so that it is importable and testable instead of being the eighty-first sibling script.
24. As a maintainer, I want the simulator to enter the Ancient room through the shipped game's own code path, so that the floor bookkeeping and every relic effect come from the game rather than from a reimplementation.
25. As a maintainer, I want the combat observation to name its encounter, so that a parity check has something to compare and an audit can identify a fight.
26. As a maintainer, I want the observation to expose the floor counter that the Ancient room advances, so that the parity gap that motivated this feature is observable instead of inferred.
27. As a maintainer, I want the published observation schema to match what the environment actually emits for run-mode captures, so that the schema stops being documentation that contradicts the code.
28. As a maintainer, I want acceptance split by seam — offline tests against the generator's public interface, shipped-game parity against the full-app seam — so that tests describe behaviour instead of internal helpers.
29. As a maintainer, I want the oracle runnable on a machine whose game install and local app-data live on different drives, so that acceptance is not silently machine-specific.
30. As a maintainer, I want the parity evidence document to record what has actually been observed at runtime, so that static conclusions are never mistaken for measurements.

## Implementation Decisions

### The parity contract

A record claims parity for one fully specified situation: the same character, Ascension, canonical run seed, Act variant, Ancient choice and nested choices, travelled to the same node coordinate. For that situation, these fields must equal what the shipped game produces. They are compared field by field, and a mismatch names the field path.

- **Run:** canonical run seed, Ascension, gold, the full set of named RNG counters, act index, act floor, total floor.
- **Combat:** turn, phase, energy, max energy, stars, encounter id.
- **Creatures:** stable id, model id, side, current and maximum HP, block, alive, next move id, that move's intents (type, damage, repeats), and powers (model id, amount).
- **Piles:** the ordered contents of hand, draw pile, discard pile, exhaust pile and play pile. Order is part of the contract — a draw pile's order is what a policy learns from, not merely its contents. Per card: instance id, model id, card type, target type, energy cost, cost-x flag, upgrades, enchantment (model id and amount), and native state.
- **Inventory:** relics in order with model id, counter and native state; potions by slot with model id.

Explicitly **not** in the contract: the simulator's state hash and any internal handle — they are simulator artifacts with no shipped-game counterpart — and anything presentational.

**Identity is compared structurally, not literally.** Card instance ids are minted by whichever encoder produced the state, so two encoders will not agree on them for the same situation. They are compared as position within an ordered pile plus the card's other attributes, unless a shared identity scheme is introduced. Identities the game itself mints — model ids, the net card id, the encounter id — are compared literally.

**The oracle must be able to compare every one of these fields, and today it cannot.** A full inventory of the full-app bridge's combat observation against the list above found roughly three dozen combat-relevant fields missing or wrong, in four categories:

- *Absent:* the encounter id; max energy; stars; the granular turn phase; every pile except the hand (the rest are counts only, and the play pile has no representation at all); card instance ids, card type, cost-x, enchantment and native state; the full intent list (only the next move's id is present); a `side` on creatures; the player's own creature row; RNG counters; act floor; map coordinate; relic counters and native states; potion slots and native states; game build.
- *Present but wrong:* act index is reported one-based where the rest of the system is zero-based; hand cards carry an upgrade-level field that is never populated, so it always reads zero; energy sits outside the combat block; hand energy cost reads a different accessor than the other projections; relics and potions are bare model-id lists, and skipping empty potion slots destroys the slot index.
- *Encoder-local:* the bridge has no card identity registry at all, so instance ids must be introduced before they can be compared structurally.
- *Vocabulary:* the bridge's phase names and the simulator's decision kinds are different words for the same situations, so the comparison needs one explicit mapping rather than a guess.

**The target shape already exists.** The trace exporter's per-combat projection is the repository's richest realization of this contract: it already carries the encounter id, the ordered draw pile, per-card identity, upgrades, enchantment, costs, the full intents and powers. The bridge's observation should converge on that projection rather than become a third shape — which is also what the existing architecture review asks for.

**The comparison is field by field, never by state hash.** The two encoders' hashes are not comparable by construction — one hashes a versioned observation plus a transition kernel, the other hashes its own DTO with neither — so a hash match would prove nothing. The comparison flattens both projections into one shape and reports the first differing field path.

**Extending the bridge is in scope; a second state projection is not.** Every missing field above is addable at the single method that builds the bridge's snapshot, and the trace exporter demonstrates that the underlying game objects are reachable from a mod assembly — with three exceptions that need an accessibility spike before this work is estimated: the act floor, the current map coordinate (a strong-typed fallback exists via the visited-coordinate list), and the attack intent list (which the trace reaches by reflection).

### Scenario identity

- A record's identity is `(character, ascension, canonical run seed, Act variant, Ancient choice index, nested choices, node coordinate)`. Two records for the same character, Ascension and seed differ only in their Ancient choice.
- **The Act variant is derived from the run seed alone.** The generator reproduces the shipped game's Act-variant roll and records the result. A caller-supplied variant override is deliberately deferred, so the first cut has exactly one source of truth for act identity.
- **The row-1 node is chosen by a fixed rule, not by the caller:** the first legal map action in the order the environment reports them, with the resulting coordinate and point type recorded. Caller-chosen nodes are deliberately deferred.
- Ancient choices are enumerated because they are a dimension of the request; nested choices are resolved, not enumerated.

### Run construction

- Runs use the shipped game's starting loadout for the requested character and Ascension. Caller-supplied decks, relics or potions are not supported: swapping them would produce a situation the shipped game cannot reach.
- Run seeds are canonicalised generator-side exactly as the shipped game does when a run begins, and the canonical form is what the request carries and the record stores. A merely non-canonical seed is accepted and canonicalised, with the raw string recorded as a diagnostic — a caller reading a seed off a screenshot should not have to know the game's input transform.
- **A canonicalisation collision is rejected, not resolved.** If two requested seeds collapse to the same canonical value, the whole request fails with an input error naming both. Silent deduplication is forbidden, because it would change the size and the balance of a corpus without telling anyone.
- The simulator enters the act-1 Ancient room at run start by travelling to the Ancient node the way the shipped game does, rather than by entering the event directly. That single decision repairs the floor bookkeeping and provides the Ancient choice dimension.
- The Ancient choice is applied through the game's own option-completion path, so that relic effects and any RNG they consume come from the game.
- The first fight is reached by travelling to a row-1 node, which is always a normal monster node and always a weak encounter.

### Observation contract

- The combat observation gains the encounter id, and the run block gains the floor counter the Ancient room advances plus act index and act floor, so that a combat observation is self-describing and the parity gap is directly observable.
- The published canonical-state schema is brought in line with what run-mode captures actually emit, instead of describing only the combat-mode shape.
- Both the observation schema version and the hash schema version are bumped. Every existing golden hash and determinism assertion is regenerated; this is cheapest now, while no generated corpus exists.
- The new fields are inside the state hash. Excluding them would stop the hash covering the state and weaken restore's divergence detection.

### Record and determinism contract

- **Row envelope.** Every row carries a versioned string schema tag and a `record_type` discriminator.
- **Success row (`record_type: "scenario"`).** Game build; the recipe — character, Ascension, canonical seed, raw seed when it differed, Act variant, the ordered Ancient options that were offered (index and relic model id each), the Ancient choice taken (index and relic model id), each nested choice resolved (kind, selected index, selected option ids), the node coordinate and point type, and the encounter id; then the combat initial state as the parity contract defines it, the RNG counters, and the state hash.
- **Failure row (`record_type: "failure"`).** Game build; the recipe resolved so far — at least character, Ascension and canonical seed, plus Act variant and Ancient choice once they are known; the stage that failed; and an error kind and message. A failure row never carries a partial combat initial state, and nothing is dropped or retried silently.
- **What "byte-identical" guarantees.** For a fixed request, game build and worker count, the emitted output is byte-identical on re-run. Concretely:
  - *Ordering.* The request expands to a deterministically ordered element list — character, then Ascension, then seed, then Ancient choice index. Shards are assigned by that element index, not by completion order, and rows within a shard are written in element order. A slow worker can change when a row appears, never where.
  - *Serialization.* Keys are written in a declared order rather than a dictionary's iteration order, encoding and separators are pinned, and every contract quantity is an integer or a string — no floats, so no formatting drift.
  - *Compression.* Compressed shards are byte-identical too, which requires pinning the gzip metadata (timestamp and embedded name) rather than letting the writer stamp the current time the way the repository's existing corpus writers do. The hard guarantee is on the decompressed rows; identical shard bytes follow once that metadata is pinned.
  - *Worker count.* Changing the worker count changes shard boundaries, so the row set is identical but the shard files are not. The guarantee is scoped to a fixed worker count; the invariant across worker counts is the row set.
- **Failure rows are deterministic too:** an element that fails fails again with the same error kind.

### Batch generator

- The generator drives the simulator, not the shipped game. The shipped game is used only as the acceptance oracle.
- Enumeration, retry, sharding and output live in the Python package; the command-line wrapper is a subcommand on the existing console entry point, following the repository's existing flag shape (worker count, character list, Ascension, output directory, compression). No new sibling script.
- Output is shards of compressed JSONL under an artifact root, one shard per worker, plus a summary file — the convention the repository already uses for corpora.
- Records carry the recipe and the combat initial state. No portable snapshot is stored; a session-scoped fast-start handle may be added later as an optimisation, explicitly not a record field.

### Oracle prerequisites

- The Python path-discovery module gains a configurable sandbox root, defaulting to the game's own volume, so that the bridge's hard links work instead of falling back to a full copy of the install. Nothing else in discovery is changed here.

## Testing Decisions

- **Test at seams, not helpers.** Two seams, two test surfaces. Offline behaviour is asserted through the generator's public package interface — the function that turns a request into rows — so canonicalisation, expansion, conflict rejection and determinism are all tested as observable behaviour rather than by calling private helpers. Shipped-game behaviour is asserted through the full-app bridge seam. If a test needs to reach inside either seam, the seam is wrong.
- **What makes a good test here:** assert on rows and on the contract field list, never on the generator's internal loop. The two things worth protecting are determinism (same request and worker count, byte-identical output) and parity (a contract field differs from the shipped game only when the game changed).
- **Offline, CI-visible (pytest under `tests/`):**
  - a request with a non-canonical seed yields rows whose recorded seed is canonical and whose raw-seed diagnostic is present;
  - a request whose seeds collide after canonicalisation is rejected, and nothing is written;
  - expansion produces exactly the expected element set, and only Ancient choices the run actually offers appear;
  - the row envelope round-trips, and every emitted row validates against the published observation schema — which is what stops the schema drifting away from the code again;
  - the same request and worker count run twice produce byte-identical shards;
  - a forced failure produces a failure row with the recipe resolved so far and no partial combat state.
- **Needs the shipped game (`*_acceptance.py` convention):** the bridge parity run. For a fixed sample of roughly a dozen scenarios spanning characters and Ascensions, drive the shipped game with the same character, Ascension, run seed, Act variant, Ancient choice and nested choices, and compare the full contract field list against the record's combat initial state, reporting the first differing field path. The comparison goes through a projection layer that normalises the bridge's observation and the record into one shape — including the phase/decision-kind vocabulary mapping and the one-based/zero-based act index — and then reuses the repository's existing per-path comparison helper, which was built for exactly this and currently has no caller. The encoders' state hashes are never compared.
- **Gate for this feature:** the fixed sample passes field by field, and determinism holds. A coverage-driven campaign — every character × every Ascension × every reachable Ancient choice — is deliberately not the gate, but is the first thing to run once the feature lands, because the nested-choice paths are where divergence is most likely. One bound is already known and must be stated by the sample itself: the bridge has no observation branch for the bundle and relic *option* picks (ticket 14 closed the card-select half of that gap), so while one of those is open it reports no legal actions and the oracle cannot advance it. Several Ancient choices open a card select, so the sample must say which nested-choice kinds it covers, and closing the remaining option-pick gap is a prerequisite before the coverage campaign can claim complete Ancient-choice coverage.
- **Prior art, and why this gap stayed invisible:** the two bridge acceptance scripts compare only whole-observation hashes and never a single field, and they are same-encoder comparisons; the one genuine field-by-field comparator works from a trace file against the simulator, and only the trace path has ever projected the state richly. Meanwhile the repository already contains a normalized per-path comparison helper built for exactly this kind of trust reporting, and it has no caller. The parity run should wire that helper up behind a projection layer rather than invent a third comparison, and should state explicitly which fields it covers.

## Out of Scope

- Caller-supplied starting loadouts. Generating "this fight with a different deck" is a different feature, and mixing it into a parity corpus would corrupt the corpus's meaning.
- A caller-supplied Act variant override, and a caller-chosen row-1 node. The first cut derives both, so that act and node identity each have exactly one source of truth.
- Enumerating nested choices as extra dimensions of the product.
- A second state projection on the bridge. The existing observation seam is extended; a parallel one would re-create the problem the architecture review already flagged.
- A shared cross-encoder state hash. The two encoders' hashes are incomparable by construction, so this feature compares fields and does not invent a common digest.
- Persisted state snapshots. The simulator's state handle is a branch identifier tied to a worker's local history, not a portable artifact.
- Acts beyond act 1, and the Ancient rooms of later acts.
- Non-parity and debug paths for forcing an Ancient choice the run does not offer.
- Repairing Steam-root discovery. It is a real defect, but it belongs to the existing single-discovery-policy work, and a configured game root is an adequate workaround for this feature.
- Scale beyond 10⁵ records.

## Further Notes

- **Two parity gaps motivate the scope, and only one of them is repaired by entering the Ancient room.** Skipping the Ancient room leaves the floor counter one entry behind the shipped game, which seeds the per-encounter generator and therefore changes randomised monster composition even when the encounter id matches — entering the room repairs that. The second gap is independent: act 1 has two Act variants, the shipped game rolls one from the run seed, and the simulator currently hard-codes the default one, so for seeds whose act 1 is the other variant every act-1 room is the wrong one. Map topology is unaffected; the pools are not. That is exactly why the first cut derives the variant from the seed and records it: without it the record is wrong for a whole class of seeds.
- **A chosen Ancient choice may legitimately change the first fight.** Some choices consume RNG that the first combat then uses for enemy HP. That is not a defect: parity is defined against a shipped-game run that made the same choice, which is why the choice is part of the record's identity rather than optional metadata.
- **Skipping the Ancient room does not shift any RNG stream.** The Ancient event draws from its own generator, so the older worry that entering it would change map, encounter or shuffle parity for a seed is settled as unfounded.
- **A pending ADR question.** The follow-up default of treating every Act variant as discovered touches `SaveManager.Progress.DiscoveredActs`, which is a discovery field, and ADR-0001 states that a fully unlocked run does not imply discovered content. When that default is implemented, ADR-0001 needs an explicit clarifying sentence or a new ADR; it should not be adopted silently.
- **Environment findings from de-risking the oracle.** The shipped game is installed in a secondary Steam library while local app-data lives on another drive, so the bridge's hard links fail and its copy fallback exhausts the local drive. The bridge itself works — real game workers start headlessly and answer — but the sandbox root must sit on the game's volume. Both this and the Steam-root discovery defect are recorded here rather than fixed broadly.
- **The oracle can now drive the card-select prompts an Ancient choice opens, and still cannot drive the option picks.** Ticket 14 took the card selector the shipped game consults before it would push a card-selection screen, so a prompt a choice opens is reported as its own stage with the offered cards named, and a caller selects one by identity. What `python/bridge_card_select_acceptance.py` measures end to end is one Ancient choice per prompt kind it drives: a one-card removal, a two-card removal, and a skippable card to add. The upgrade, transform and discard prompts reach the same seam and are read from the decompiled build's own call sites rather than measured. What remains outside the oracle is the *option* pick (`option_choice`): a bundle (`SCROLL_BOXES`) or a relic pick has no selector branch in the shipped game, so its screen appears and the shipped autoplay's own handler answers it, which the same acceptance records as a measurement. Ticket 15's sample must name that kind as one it cannot drive, so the bound is now exact rather than general.
- **Evidence and its limits.** `.scratch/act1-combat1-scenarios/parity-findings.md` separates what has been read from the decompiled build from what has actually been observed at runtime, and states plainly that no field-by-field comparison has run yet.
