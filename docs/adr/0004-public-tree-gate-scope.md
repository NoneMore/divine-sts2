# The public-tree gate scans machine paths outside documentation

`scripts/test-public-tree.ps1` rejects tracked files that name a machine-specific user or library path, and it has to be able to run on the tree it gates. A gate whose own finding cannot be written down is a gate that cannot explain itself: the B1 entry in `docs/architecture-review.md` became the third match the moment it quoted the pattern and the two files it matched, so the review document failed the check it documented and CI went red on a pristine `main`. Machine-path scanning therefore skips tracked markdown, while the secret-token scan keeps covering every tracked file, because a credential leaked into prose is still a leak. Keeping markdown inside the path scan and requiring placeholder spellings was rejected: it converts a policy into a spelling convention enforced by an unexplained build failure, which is exactly what the B1 write-up had to work around.

**The rule binds the documents, not just the scanner.** Documentation may describe a leak in the accusatory and never in the quotable: "a secondary Steam library", `%USERPROFILE%`, `<repo>\.tools`, never a drive-qualified path. Excluding markdown is what makes that a writing convention rather than a build break, so a reviewer is the only enforcement the path rule needs in prose — which is why the secret scan, which needs no such judgment, was not narrowed alongside it.
