# Sandbox adaptation is conditional and lives in shared helpers

Adapting to an unusual Windows host — a read-only user profile, a proxy that refuses `curl` and `Invoke-WebRequest` downloads, a sandbox that denies absolute paths — must not change what a normal host does. Each adaptation therefore probes its condition, does nothing when the condition is absent, and lives in a shared entry point (`scripts/common.ps1`, `python/sts2_native_sim/paths.py`, `NativeWorker`) rather than in global build configuration or in a block each call site copies. Global configuration changes what everyone gets: hardcoding a game path, forcing a single build node, or disabling `NuGetAudit` in `Directory.Build.props` would make every other environment slower, narrower, or unaudited to accommodate one machine. Disabling the audit therefore stays an explicit documented flag rather than a detection, and `-m:1` is applied only when the SDK cannot resolve its own workload-locator directories. The same reasoning removes discovery's fallback to a sibling checkout's `.tools`: a borrowed toolchain is precisely the thing that disappears mid-session, and a repository that quietly builds against it produces a machine-specific result that looks reproducible.

**Every adaptation is recorded where it can be re-checked.** A probe in a shared helper, a test under `tests/`, or a short entry in `docs/agents/dev-environment.md` — never a prose instruction to export four variables before running something, which is what the repository had. An explicit `-Sandbox` switch was rejected for the same reason the prose was: it requires the next reader to already know the situation exists, which is the failure this decision removes. Unconditional redirection into the repository was rejected because it changes behaviour on hosts that have no problem, and `.env` is read only to fill variables that are not already set, so a real environment never loses to a file in the working tree.
